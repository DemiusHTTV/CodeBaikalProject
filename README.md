# CodeBaikal — SQL-ассистент для университета

Сотрудник вуза задаёт вопрос по-русски — система переводит его в SQL, проверяет
на безопасность, выполняет на PostgreSQL и показывает результат таблицей вместе
с самим запросом.

```
Вопрос (рус.) → YandexGPT → SQL → 8 проверок → PostgreSQL (read-only) → таблица
```

Доступ разграничен по ролям через JWT: абитуриент, студент, преподаватель и
сотрудник видят разные таблицы, а персональные данные студентов и абитуриентов
выдаются только в обобщённом виде.

---

## Быстрый старт

Нужны **три терминала** — база, бэкенд и фронтенд работают одновременно.

### 0. Один раз: настроить `.env`

```bash
cp .env.example .env
```

Заполнить `YANDEX_AUTH` / `YANDEX_FOLDER` (ключ и каталог Yandex Cloud) и
сгенерировать свой секрет для токенов:

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"   # → в JWT_SECRET
```

### Терминал 1 — база данных

```bash
cd backend/db
docker compose up -d
```

При первом запуске Postgres сам выполнит `schema.sql` и `seed.sql` — получится
база с 14 таблицами и тестовыми данными (854 студента, 5627 заявлений).
Это единственный из трёх процессов, который живёт в фоне.

### Терминал 2 — бэкенд

```bash
cd backend
DB_HOST=127.0.0.1 DB_PORT=5432 DB_NAME=university DB_USER=hackathon DB_PASSWORD=hackathon \
  .venv/bin/uvicorn src.main:app --port 8000 --reload
```

Ждём `Application startup complete`. Терминал не закрывать — здесь видно все
запросы от фронта.

> Переменные перед командой перебивают `.env` — так удобно работать с локальной
> базой, не трогая файл. Если `.env` уже указывает на нужную БД, префикс не нужен.

### Терминал 3 — фронтенд

```bash
cd frontend
npm install     # только в первый раз
npm run dev
```

Открыть <http://localhost:5173>.

### Проверка, что связка работает

Выбрать роль → «Начать» → нажать любую подсказку. В терминале 2 должны появиться
строки `POST /api/login 200 OK` и `POST /api/ask 200 OK`. Если в браузере ошибка,
а в терминале 2 тихо — запрос не ушёл, смотреть консоль браузера (F12).

## Как всё связано

```
браузер :5173  ──POST /api/ask──▶  бэкенд :8000  ──SQL──▶  postgres :5432
   React                             FastAPI                  Docker
```

Адрес бэкенда фронт берёт из `frontend/src/api.js`, обратную сторону разрешает
список CORS в `backend/src/main.py`. **Порты нельзя менять по отдельности:**
поменяли порт бэкенда — правьте `api.js`, поменяли порт фронта — правьте CORS.

## Консольный режим (без браузера)

Альтернатива фронту, а не дополнение — бэкенд для него запускать не нужно,
он ходит в базу напрямую:

```bash
cd backend
DB_HOST=127.0.0.1 DB_PORT=5432 DB_NAME=university DB_USER=hackathon DB_PASSWORD=hackathon \
  .venv/bin/python -m src.ask
```

Спрашивает роль, выпускает настоящий JWT, дальше — вопросы по-русски.
Пустая строка — выход.

## Роли и доступ

| Роль | Таблицы | ФИО студентов/абитуриентов |
|---|---|---|
| `applicant` | справочники + приёмная кампания | нет |
| `student` | справочники + `students`, `grades` | нет, и только **свои** оценки |
| `teacher` | справочники + `students`, `grades` | нет |
| `staff` | все | да |

Роль берётся **только из подписанного JWT**, никогда из тела запроса — прислать
`"role": "staff"` и получить чужие права не выйдет.

Для роли `student` в токен кладётся `student_id`: запрос с чужим id отклоняется
на уровне проверки SQL, а не только просьбой к модели.

## API

```
POST /api/login   {"role": "student", "student_id": 1}   → {"token": "...", ...}
POST /api/ask     {"question": "..."}                     → {"sql", "columns", "rows", ...}
                  заголовок: Authorization: Bearer <token>
GET  /api/health                                          → {"status": "ok"}
```

Пример через curl:

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/login \
  -H 'Content-Type: application/json' \
  -d '{"role":"staff"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['token'])")

curl -s -X POST http://127.0.0.1:8000/api/ask \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"question":"Сколько студентов на факультете информационных технологий?"}'
```

Интерактивная документация — <http://127.0.0.1:8000/docs>.

## Безопасность: три независимых рубежа

**1. До модели.** Промпт собирается под роль: в схеме, которую видит YandexGPT,
есть только разрешённые роли таблицы. Абитуриент не знает о существовании
`grades`, поэтому и запроса к ней не сгенерирует.

**2. После модели.** `sql_guard/` — восемь проверок, каждая в своём файле.
Разбор идёт по дереву запроса (`sqlglot`), а не поиском слов в тексте, поэтому
опасное нельзя спрятать в комментарий, регистр или подзапрос:

| Файл | Что отсекает |
|---|---|
| `parsing.py` | не-SQL, два оператора через `;`, markdown-обёртку от модели |
| `no_writes.py` | любую запись, **включая спрятанную в CTE** |
| `no_locks.py` | `FOR UPDATE` / `FOR SHARE`, в том числе в подзапросе |
| `tables.py` | системные каталоги и таблицы вне роли |
| `functions.py` | `pg_read_file`, `pg_sleep`, `dblink` и другие опасные функции |
| `no_raw_pii.py` | вывод ФИО студентов, **включая через `SELECT *`** |
| `own_rows.py` | чужой `student_id` |
| `limits.py` | отсутствие `LIMIT` (по умолчанию 200, максимум 1000) |

Про `no_raw_pii`: проверяется то, что уходит **в вывод**, а не любое упоминание
колонки. `SELECT count(*) ... WHERE full_name LIKE 'А%'` разрешён — он возвращает
число и никого не называет. `SELECT full_name FROM students` запрещён.

**3. В базе.** Запрос выполняется в `READ ONLY` транзакции с `statement_timeout` —
даже если что-то просочится, PostgreSQL сам откажется что-либо менять.

## Логи и аналитика

Логи пишутся в `backend/logs/app.log`, по одной JSON-записи на строку. На каждый
вопрос — одна сводная запись со всеми полями:

```json
{"event": "ask", "request_id": "6dc705303344", "role": "student",
 "question": "Какие у меня оценки?", "sql": "SELECT ... LIMIT 200",
 "outcome": "ok", "row_count": 5, "elapsed_ms": 1566}
```

`request_id` нужен, чтобы при параллельной работе нескольких человек можно было
понять, какая строка к какому вопросу относится.

Отчёт по логам:

```bash
cd backend
.venv/bin/python -m src.analytics
```

Показывает разрез по ролям, чем закончились запросы, время ответа (медиана и
95-й процентиль), что отклонила защита и — самое полезное — **вопросы, которые
отработали, но вернули пусто**: формально успех, а человеку не помогли.

## Структура

```
backend/
├── db/
│   ├── docker-compose.yml    локальный Postgres
│   ├── schema.sql            14 таблиц
│   └── seed.sql              тестовые данные
├── src/
│   ├── main.py               HTTP API (FastAPI)
│   ├── ask.py                консольный чат
│   ├── analytics.py          отчёт по логам
│   ├── pipeline.py           ядро: вопрос → SQL → проверка → БД
│   ├── llm.py                клиент YandexGPT
│   ├── prompt.py             сборка промпта под роль
│   ├── auth.py               выпуск и проверка JWT
│   ├── roles.py              роль → доступные таблицы и ПДн
│   ├── sql_guard/            8 проверок SQL
│   ├── db.py                 пул соединений, read-only транзакции
│   ├── config.py             настройки из .env
│   ├── schema_context.py     разбор schema.sql
│   └── logging_config.py     JSON-логи
└── Tests/

frontend/
└── src/
    ├── App.jsx               переключатель вход / чат
    ├── LoginScreen.jsx       выбор роли
    ├── ChatScreen.jsx        чат, подсказки, состояния
    ├── Message.jsx           сообщение / загрузка / ошибка
    ├── ResultTable.jsx       таблица результата
    ├── api.js                единственное место с адресом бэкенда
    └── styles.css

 Questions_Tests/ Скриншоты 31 вопроса и то как он на них  модель на них ответила

```

Принцип разбиения: каждый файл знает только про свой слой. `llm.py` не знает,
что такое SQL; `sql_guard` не знает про HTTP; `db.py` не знает про роли. Поэтому
замена GigaChat на YandexGPT затронула ровно один файл.

## Частые проблемы

**`address already in use`** — порт занят прошлым запуском:

```bash
ss -ltnp | grep :8000
pkill -f "uvicorn src.main"
```

**Фронт пишет «Не удалось войти»** — бэкенд не запущен или упал, смотреть терминал 2.

**Бэкенд падает на старте** — не поднята база, вернуться к терминалу 1.

**`KeyError: 'JWT_SECRET'`** — не заполнен `.env`, см. шаг 0.

**Запрос вернул пусто** — модель могла выбрать не ту таблицу или не угадать
точное значение в тексте. Такие случаи видно в `python -m src.analytics`,
лечатся подсказками в `src/prompt.py`.

## Что пока не сделано

- Ответ не пересказывается словами — показываем таблицу и SQL, а не фразу
  «на факультете учится 246 студентов» (это второй вызов модели).
- Нет петли самокоррекции: если проверка отклонила SQL, мы объясняем причину,
  а не просим модель переписать запрос.
- Чат — отдельное веб-приложение, а не встраиваемый виджет.
- `teacher` и `student` пока имеют одинаковый набор таблиц.
